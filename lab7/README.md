# Lab 7

## Что показывает эта лабораторная

В `lab7` показан паттерн `Transactional Outbox`.

Смысл такой:

- приложение сохраняет пользователя в таблицу `users`;
- в той же транзакции сохраняет событие в таблицу `outbox`;
- отдельный воркер читает события из `outbox` и "отправляет" их дальше.

Это нужно, чтобы не было ситуации, когда пользователь уже записан в базу, а событие о нем потерялось.

## Из чего состоит проект

- `db`:
  контейнер MySQL.
- `web`:
  PHP-FPM с приложением.
- `nginx`:
  принимает HTTP-запросы на `localhost:8080` и передает их в PHP.
- `outbox-worker`:
  отдельный контейнер, который постоянно проверяет таблицу `outbox`.

## Какие таблицы создаются

Файл `init.sql` создает:

- `users`:
  таблица пользователей;
- `outbox`:
  таблица событий, которые нужно обработать после успешной транзакции.

## Как работает сценарий

Когда открывается `http://localhost:8080`:

1. Приложение подключается к базе.
2. Генерирует тестового пользователя.
3. Сохраняет пользователя в `users`.
4. В той же транзакции записывает событие `UserRegistered` в `outbox`.
5. Подтверждает транзакцию.
6. Воркер видит новое событие.
7. Воркер обрабатывает его и удаляет из `outbox`.

Здесь нет настоящего Kafka или RabbitMQ. Вместо этого воркер просто пишет в лог, что событие обработано. Для лабораторной этого достаточно: видно сам механизм `Transactional Outbox`.

## Что видно в логах

После запуска в логах видно:

- запуск воркера;
- ожидание готовности базы;
- каждый опрос таблицы `outbox`;
- новый HTTP-запрос;
- старт транзакции;
- вставку пользователя в `users`;
- вставку события в `outbox`;
- коммит транзакции;
- выбор события воркером;
- обработку и удаление события из `outbox`.

## Команды для запуска

Перейти в папку лабораторной:

```bash
cd lab7
```

Поднять контейнеры:

```bash
docker compose up --build
```

Поднять контейнеры в фоне:

```bash
docker compose up -d --build
```

Остановить лабораторную:

```bash
docker compose down
```

Остановить лабораторную и удалить том с базой:

```bash
docker compose down -v
```

## Команды для проверки

Посмотреть все логи:

```bash
docker compose logs -f
```

Посмотреть только логи воркера:

```bash
docker compose logs -f outbox-worker
```

Посмотреть только логи веб-приложения:

```bash
docker compose logs -f web
```

Сделать один запрос к приложению в PowerShell:

```bash
Invoke-WebRequest http://localhost:8080 | Select-Object -ExpandProperty Content
```

Сделать несколько запросов подряд в PowerShell:

```bash
1..3 | ForEach-Object { Invoke-WebRequest http://localhost:8080 | Select-Object -ExpandProperty Content }
```

Проверить пользователей в базе:

```bash
docker compose exec db mysql -uapp_user -papp_pass app_db -e "SELECT id, email, name, created_at FROM users ORDER BY id DESC;"
```

Проверить содержимое `outbox`:

```bash
docker compose exec db mysql -uapp_user -papp_pass app_db -e "SELECT id, aggregate_id, event_type, status, created_at FROM outbox ORDER BY id DESC;"
```

## Какой результат считается правильным

Правильный сценарий выглядит так:

1. Вы запускаете `docker compose up --build`.
2. В логах воркера видно, что он подключился к базе и начал опрашивать `outbox`.
3. Вы вызываете `Invoke-WebRequest http://localhost:8080 | Select-Object -ExpandProperty Content`.
4. В логах `web` видно создание пользователя и запись события в `outbox`.
5. В логах `outbox-worker` видно, что событие найдено, обработано и удалено.
6. В таблице `users` появляется новая запись.
7. В `outbox` не остается свежих событий со статусом `PENDING`.

## Короткий вывод

Эта лабораторная показывает надежный способ связать изменение данных в базе и публикацию событий. Сначала приложение сохраняет и данные, и событие в одной транзакции, а потом отдельный воркер безопасно обрабатывает событие из `outbox`.
