# **Архитектурное решение: Проектирование веб\-системы с использованием современных паттернов**

**Лабораторная работа №6**  
В данном документе представлено подробное описание архитектуры отказоустойчивой, масштабируемой веб\-системы (на примере маркетплейса/системы заказов) с применением инфраструктурных и прикладных паттернов проектирования.  
 

## **1\. Архитектура системы**

В основе системы лежит классическая **трёхзвенная архитектура (Three-Tier Architecture)**, обеспечивающая жесткое разделение ответственности:

* **Презентационный уровень (Client):** Веб- и мобильное приложение. Разработаны по принципу **тонкого клиента (Thin Client)**. Это значит, что вся ключевая бизнес-логика, расчеты стоимости, правила валидации и маршрутизация данных вынесены на сторону бэкенда. Клиент отвечает исключительно за отрисовку интерфейса (UI) и отправку запросов, что упрощает обновление логики без необходимости форсированного обновления приложений пользователями.  
* **Уровень приложений (Backend):** Набор микросервисов, скрытых за единой точкой входа (API Gateway), выполняющих обработку запросов.  
* **Уровень данных (Database):** Реляционные базы данных для надежного хранения информации и документо-ориентированные/In-Memory хранилища для быстрого доступа.

 

## **2\. Взаимодействие сервисов и инфраструктура**

Для обеспечения гибкости и масштабируемости микросервисной сети внедрены три базовых инфраструктурных компонента:

| Паттерн | Принцип работы в системе | Назначение / Решаемая задача   |
| :---- | :---- | :---- |
| **Service Discovery** | Центральный реестр (например, Consul или Eureka), где каждый запущенный инстанс сервиса регистрирует свой сетевой адрес (IP:порт). | Динамическое обнаружение сервисов. API Gateway запрашивает адреса у реестра, избавляя от жесткой привязки конфигураций к IP-адресам. |
| **Heartbeat** | Каждый микросервис с регулярным интервалом (например, каждые 5-10 секунд) отправляет фоновый ping-запрос в Service Discovery. | Контроль "живучести" инстансов. Если сервис перестает присылать сигналы, реестр исключает его из маршрутизации, предотвращая отправку трафика на сломанный узел. |
| **Pub/Sub (Publish/Subscribe)** | Шина сообщений (на базе Apache Kafka или RabbitMQ). При изменении статуса заказа (например, "Оплачен") сервис заказов публикует событие в брокер, не зная о получателях. | Асинхронное уведомление других систем. Подписчики (Сервис доставки, Сервис нотификаций) самостоятельно забирают событие из очереди и обрабатывают его. |

 

## **3\. Работа с данными: CQRS и MapReduce**

### **Паттерн CQRS (Command Query Responsibility Segregation)**

Для оптимизации работы под нагрузкой операции записи и чтения полностью разделены на уровне кода и баз данных:

* **Модель записи (Commands):** Обрабатывает операции создания и изменения (например, создание заказа). Данные пишутся в транзакционную БД (PostgreSQL), оптимизированную под ACID-требования и нормализацию.  
* **Модель чтения (Queries):** Предназначена для молниеносной выдачи информации пользователю (например, просмотр истории заказов). Чтение направляется в денормализованную базу данных или In-Memory кэш (Redis), где данные хранятся в максимально готовом для отображения виде. Синхронизация между моделями происходит асинхронно через шину Pub/Sub.

### **Аналитическая обработка данных (MapReduce)**

Для тяжелых расчетов (например, подсчет ежедневной выручки по категориям или выявление трендов) используется модель распределенных вычислений MapReduce:

1. **Этап Map (Разделение):** Огромный массив транзакционных логов распределяется по нескольким узлам. Каждый узел выбирает только целевые пары данных, например: \[Категория: "Электроника", Сумма: 5000\].  
2. **Этап Reduce (Свертка):** Данные с одинаковыми ключами (категориями) агрегируются на финальных узлах, суммируя показатели. Результат записывается в аналитическую БД для построения дашбордов руководству.

 

## **4\. Отказоустойчивость и надежность**

В распределенной среде временные сбои неизбежны. Для предотвращения каскадных аварий внедрены пять защитных механизмов:

* **Retries \+ Backoff (Повторные запросы):** Если сервис платежей вернул ошибку сети, бэкенд повторит попытку через 1 секунду, затем через 2, 4 и 8 секунд (экспоненциальный рост паузы — Exponential Backoff). Это снижает лавинообразную нагрузку на восстанавливающийся целевой сервис.  
* **Idempotency (Идемпотентность):** Каждому запросу на оплату или создание заказа клиент присваивает уникальный ключ (Idempotency-Key). Если из\-за сетевого сбоя клиент отправит запрос повторно, система обнаружит ключ-дубликат и просто вернет уже готовый результат прошлой успешной операции, исключив двойное списание денег.  
* **Circuit Breaker ("Предохранитель"):** Если сторонний сервис (например, интеграция с банком) начинает стабильно выдавать ошибки (более 50% запросов за минуту), предохранитель "размыкает цепь". Все последующие запросы к банку мгновенно блокируются на уровне API Gateway, не тратя ресурсы системы на ожидание заведомо провального тайм-аута. Через время цепь переходит в "полуоткрытое" состояние для проверки одной пробной транзакцией.  
* **Backpressure (Управление давлением трафика):** Если во время распродажи воркеры фоновой обработки не справляются с очередью заказов, они сигнализируют API Gateway о перегрузке. Система начинает искусственно ограничивать скорость приема новых низкоприоритетных запросов на входе, защищая базу данных от падения.

### **Стратегии обработки критических ошибок:**

* **Fallback (Альтернативный путь):** Если рекомендательная нейросеть недоступна, Circuit Breaker перенаправляет запрос на Fallback-метод, который отдает пользователю статичный список топ-продаж вместо персональных рекомендаций.  
* **Graceful Degradation (Плавное снижение функциональности):** При критической перегрузке система отключает "тяжелые" второстепенные блоки интерфейса (например, отзывы, блок похожих товаров или анимации статусов), сохраняя работоспособность главного бизнес-сценария — возможности оформить и оплатить заказ.

 

## **5\. Кэширование данных**

Для минимизации запросов к дисковой БД активно используется кэширование в Redis со следующими паттернами:

* **Версионирование кэша:** Каждая запись кэша снабжается версией или заголовком ETag. При изменении логики или структуры данных на бэкенде инкрементируется глобальная версия кэша (например, с v1 на v2), что заставляет систему игнорировать старые объекты и исключает чтение поврежденных или неактуальных структур.  
* **Тегирование кэша:** Кэшированные объекты связываются с тегами сущностей. Например, профиль пользователя и его корзина кэшируются с тегом  
  `user_1524`. При выходе пользователя из аккаунта или смене пароля система отправляет команду на инвалидацию (удаление) всех записей, помеченных этим конкретным тегом, не затрагивая остальной кэш глобально.

 

## **6\. Асинхронная обработка и отложенные задачи**

Для поддержания высокой скорости отклика интерфейса тяжелые операции выносятся из основного потока выполнения (Request-Response):

* **Очередь сообщений (Message Queue):** При нажатии кнопки "Купить" бэкенд лишь проверяет остаток товара на складе, генерирует задачу в очередь (RabbitMQ/Kafka) и мгновенно возвращает клиенту статус "Заказ принят в обработку".  
* **Отложенные задачи и Worker-процессы:** Изолированные фоновые процессы (Воркеры) считывают задачи из очереди в своем темпе. Они осуществляют генерацию PDF-чеков, списание бонусов, отправку писем и обновление аналитики, избавляя пользователя от необходимости смотреть на экран загрузки.

 

## **7\. Способы получения статусов клиентом**

Поскольку обработка заказов происходит асинхронно на воркерах, клиенту нужно узнать, когда статус изменится на "Готов". Рассмотрены три стратегии:

1. **Polling (Короткие опросы):** Клиент раз в 5 секунд отправляет стандартный HTTP-запрос  
   `GET /orders/1/status`. Бэкенд сразу отвечает текущим статусом. *Минус:* создает огромную паразитную нагрузку на сеть, если статус долго не меняется.  
2. **Long Polling (Длинные опросы):** Клиент отправляет запрос, но бэкенд не возвращает ответ сразу, а удерживает HTTP-соединение открытым до тех пор, пока статус заказа не изменится в БД (или не выйдет таймаут). Как только статус обновился — сервер отвечает, клиент закрывает соединение и открывает новое. Это значительно экономит ресурсы сети.  
3. **Streaming (Потоковая передача / WebSockets или SSE):** Клиент открывает постоянное двустороннее соединение с сервером. При изменении статуса в шине Pub/Sub сервер мгновенно "проталкивает" (push) событие в открытый веб\-сокет клиента в режиме Near Real-Time. Идеально подходит для трекинга курьера на карте или live-обновлений.

 

## **8\. Стратегии деплоя и релиза новой функциональности**

| Стратегия деплоя | Суть метода | Преимущества и применимость   |
| :---- | :---- | :---- |
| **Rolling Release** | Поэтапное обновление инстансов сервиса. Из 10 запущенных серверов старой версии v1 выключаются два, вместо них запускаются два с версией v2. Процесс повторяется, пока все узлы не обновятся. | Отсутствие простоя системы (Zero Downtime). Не требует удвоения серверных мощностей. |
| **Blue/Green Release** | Параллельно разворачиваются два идентичных производственных окружения. Blue — текущая рабочая версия (v1), Green — новая (v2). После полного тестирования Green окружения, балансировщик (Nginx) за одну секунду переключает 100% трафика на него. | Максимально безопасный деплой. В случае обнаружения бага можно мгновенно переключить балансировщик обратно на Blue (Rollback за секунду). Требует x2 ресурсов. |
| **Canary Release ("Канареечный релиз")** | Новая версия v2 раскатывается на минимальное количество серверов, и балансировщик направляет туда лишь малую долю реального трафика (например, 5% пользователей или только внутренним сотрудникам). | Минимизация бизнес-рисков. Если у "канареечной" группы пользователей не возникает ошибок, деплой продолжается на остальные 95% пользователей. |

 

## **Ответы на контрольные вопросы задания**

1. **Какие паттерны использованы и зачем?**  
   Использована трехзвенная модель с тонким клиентом для безопасности и централизации логики. CQRS разделяет операции чтения и записи для максимального масштабирования БД. Очереди сообщений и асинхронные воркеры разгружают основной поток API. Паттерны надежности защищают от сбоев интеграции с внешними системами (банками, службами доставки), а кэширование снижает нагрузку на диски.  
2. **Как обеспечена отказоустойчивость?**  
   Отказоустойчивость достигается за счет изоляции сбоев. Внедрение Circuit Breaker предотвращает зависание потоков бэкенда при отказе внешних сервисов, переводя трафик на альтернативные пути (Fallback). Повторные попытки с задержкой (Retries \+ Backoff) нивелируют минутные моргания сети, а идемпотентность защищает от дублирования транзакций при повторах со стороны клиента.  
3. **Как масштабируется система?**  
   Система масштабируется горизонтально. Благодаря Service Discovery новые инстансы микросервисов могут запускаться автоматически под нагрузкой и сразу принимать трафик. Балансировщик эффективно распределяет HTTP-запросы. Разделение баз данных через CQRS позволяет бесконечно наращивать количество реплик на чтение (Redis/Read-PostgreSQL), а тяжелые задачи перемалываются в фоне независимыми воркерами.
