# **Архитектурное решение: Система учёта доходов и расходов с масштабированием**

Данный документ представляет собой готовое решение лабораторной работы по проектированию отказоустойчивой и масштабируемой архитектуры базы данных для системы «Кошелёк расходов/доходов».

## ---

**Задание 1: Проектирование базы данных**

Для системы учёта финансов выбрана реляционная модель данных, так как транзакции требуют строгой согласованности (ACID).

### **Описание таблиц и полей**

* **users (Пользователи)**  
  * user\_id (UUID, PK) — уникальный идентификатор пользователя.  
  * email (VARCHAR) — электронная почта (уникальное поле).  
  * password\_hash (VARCHAR) — хэш пароля.  
  * created\_at (TIMESTAMP) — дата регистрации.  
* **accounts (Счета)**  
  * account\_id (UUID, PK) — уникальный идентификатор счёта.  
  * user\_id (UUID, FK) — владелец счёта.  
  * name (VARCHAR) — название (например, «Дебетовая карта», «Наличные»).  
  * currency (VARCHAR) — валюта счёта (RUB, USD и т.д.).  
  * balance (NUMERIC) — текущий баланс.  
* **categories (Категории)**  
  * category\_id (UUID, PK) — уникальный идентификатор категории.  
  * user\_id (UUID, FK, Nullable) — создатель категории (null для системных категорий, доступных всем).  
  * name (VARCHAR) — название («Продукты», «Зарплата»).  
  * type (VARCHAR) — тип («income» — доход, «expense» — расход).  
* **transactions (Транзакции)** — *самая высоконагруженная таблица*  
  * transaction\_id (UUID) — часть составного PK.  
  * account\_id (UUID, FK) — ссылка на счёт.  
  * category\_id (UUID, FK) — ссылка на категорию.  
  * amount (NUMERIC) — сумма операции.  
  * transaction\_date (TIMESTAMP) — дата и время проведения. Часть составного PK.  
  * description (TEXT) — комментарий к платежу.  
* **monthly\_aggregates (Агрегаты)** — таблица для быстрого построения отчётов.  
  * aggregate\_id (UUID, PK) — идентификатор записи.  
  * user\_id (UUID, FK) — ссылка на пользователя.  
  * year\_month (VARCHAR) — месяц отчёта (например, «2026-06»).  
  * total\_income (NUMERIC) — общий доход за месяц.  
  * total\_expense (NUMERIC) — общий расход за месяц.

### **Связи между сущностями**

* Один пользователь может иметь много счетов (users.user\_id \-\> accounts.user\_id, 1:M).  
* Один счёт может содержать множество транзакций (accounts.account\_id \-\> transactions.account\_id, 1:M).  
* В одной категории может быть множество транзакций (categories.category\_id \-\> transactions.category\_id, 1:M).  
* У одного пользователя может быть множество записей агрегатов (users.user\_id \-\> monthly\_aggregates.user\_id, 1:M).

**Задание 2: Партиционирование**

Наибольший объём данных в системе занимает таблица **transactions** (Транзакции).

* **Тип партиционирования:** Секционирование по диапазонам (Range Partitioning).  
* **Критерий (ключ партиционирования):** Поле transaction\_date.  
* **Структура партиций:** Данные делятся по временным интервалам — **один месяц на одну партицию** (например, transactions\_2026\_05, transactions\_2026\_06).

### **Обоснование и ускорение запросов**

Пользователи чаще всего смотрят историю операций за текущий или прошлый месяц. СУБД автоматически исключает из поиска партиции, не подходящие под временной фильтр (Partition Pruning).  
**Ускоряются запросы:** Выборка истории за конкретный период, расчёт аналитики за месяц.

**Задание 3: Шардирование**

Для горизонтального масштабирования базы данных на несколько серверов применяется шардирование.

* **Способ шардирования:** Хэш-шардирование (Hash-based partitioning).  
* **Ключ шардирования (Shard Key):** Поле user\_id.  
* **Алгоритм распределения:** Использование хэш-функции от ID пользователя и остатка от деления: Shard\_ID \= CRC32(user\_id) % N, где N — количество шардов.  
* **Количество шардов:** На старте закладывается 4 шарда (физических сервера или кластера).

### **Где хранятся данные?**

Все данные конкретного пользователя (его профиль, счета, категории, транзакции и агрегаты) гарантированно находятся **на одном и том же шарде**. Нужный шард определяется маршрутизатором (API-сервисом) в момент выполнения запроса по его user\_id. Это позволяет избежать тяжёлых межсерверных запросов (Cross-shard JOINs).

## ---

**Задание 4: Репликация**

Для обеспечения высокой доступности и отказоустойчивости каждый шард представляет собой группу серверов, организованных по схеме **Master-Replica (один ведущий, два ведомых)**.

### **Потоки данных**

* **Куда идут записи:** Все изменяющие операции (INSERT, UPDATE, DELETE) направляются строго на **Master-сервер** текущего шарда.  
* **Откуда читаются данные:** Чтение истории операций, баланса и аналитики (SELECT) происходит с **Replica-серверов**, что разгружает основной сервер. Репликация асинхронная.

### **Поведение при сбоях**

Если Master-сервер выходит из строя, система мониторинга (например, Orchestrator или Patroni) фиксирует аварию. Один из Replica-серверов с наиболее актуальными данными автоматически продвигается до роли нового Master. API-маршрутизатор перенаправляет поток записи на него. Время простоя (Failover) составляет несколько секунд.

## ---

**Задание 5: Архитектура системы**

Архитектура представляет собой распределённую систему:

1. **Клиентские приложения** (Мобильное приложение / Web) отправляют запросы.  
2. **Балансировщик (Nginx / HAProxy)** распределяет запросы между экземплярами бэкенда.  
3. **Бэкенд-сервисы (API Gateway)** извлекают user\_id, вычисляют целевой шард и отправляют SQL-запрос на нужную группу серверов.  
4. **Слой хранения** состоит из 4 шардов, внутри каждого настроена репликация, а в таблице транзакций — помесячное партиционирование.

## ---

**Задание 6: Анализ**

### **1\. Почему выбран данный способ шардирования?**

Хэширование по user\_id обеспечивает максимально равномерное распределение пользователей и их транзакций по серверам. Это предотвращает появление «горячих» серверов (когда один сервер перегружен, а остальные простаивают), что часто случается при шардировании по алфавиту или географии.

### **2\. Какие преимущества даёт партиционирование?**

* **Быстрое удаление старых данных:** Вместо тяжёлого DELETE FROM transactions WHERE date \< ..., который блокирует таблицы, можно мгновенно сбросить старую партицию через DROP TABLE.  
* **Локализация индексов:** Индексы строятся для каждой партиции отдельно, они занимают меньше места в оперативной памяти, что ускоряет поиск.

### **3\. Возможные проблемы системы**

* **Эффект «крупного клиента» (Hotspots):** Если один из пользователей — это микропредприятие с миллионами транзакций, его шард будет расти значительно быстрее других.  
* **Сложность глобальной аналитики:** Если потребуется посчитать общую сумму транзакций всех пользователей системы, придётся делать запросы ко всем шардам и объединять результаты на бэкенде.

### **4\. Способы масштабирования**

* **Добавление шардов (Решардинг):** При нехватке места увеличивается N в формуле хэширования, и часть данных переносится на новые серверы (для минимизации оверхэда применяется консистентное хэширование).  
* **Балансировка чтения:** При росте нагрузки на чтение в рамках одного шарда можно просто добавить дополнительные Replica-серверы, не трогая основную структуру.
