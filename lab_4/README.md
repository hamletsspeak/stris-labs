# Лабораторная работа 4

Проектирование БД для системы учета доходов и расходов с использованием партиционирования, шардирования и репликации.

## Идея работы

Система "кошелек доходов и расходов" со временем накапливает очень много транзакций. Пока пользователей мало, все можно хранить в одной базе и в одной большой таблице. Но когда данных становится много, появляются три типичные проблемы:

- отчеты за период начинают работать медленнее;
- одной базы становится тяжело обслуживать всех пользователей;
- отказ одного сервера может остановить чтение или запись.

Поэтому в этой работе используется сразу три подхода:

- `партиционирование` помогает разделить большую таблицу на части;
- `шардирование` распределяет пользователей по разным серверам;
- `репликация` делает копии данных для отказоустойчивости и чтения.

## Простое объяснение терминов

### Что такое партиционирование

Партиционирование - это разделение одной большой таблицы на несколько логических частей внутри одной базы данных.

В нашем случае самая большая таблица - `transactions`, потому что именно в ней хранится история всех операций. Логично делить ее по времени: например, отдельно транзакции за май 2026, отдельно за июнь 2026 и так далее.

Это удобно потому, что запросу не нужно просматривать всю историю сразу. Если пользователь строит отчет только за июнь, база обращается только к июньской партиции, а не ко всей таблице.

Важно: для приложения это по-прежнему одна таблица `transactions`. Разделение происходит на уровне хранения данных.

### Что такое шардирование

Шардирование - это разделение данных уже не внутри одной таблицы, а между разными серверами или экземплярами базы данных.

В этой работе данные распределяются по `user_id`. Это значит, что данные одного пользователя стараются хранить в одном шарде: его счета, категории, транзакции и агрегаты попадают в один и тот же узел.

Такой подход удобен для систем учета личных финансов, потому что большинство запросов относятся к одному пользователю. Значит, их можно выполнить внутри одного шарда без лишнего обмена данными между серверами.

### Что такое репликация

Репликация - это создание копий данных одного и того же шарда на других серверах.

Обычно есть один основной узел `primary` или `master`, в который идут записи, и одна или несколько `replica`, из которых можно читать данные. Это нужно по двум причинам:

- если основной узел временно недоступен, систему проще восстановить;
- чтение можно распределить по репликам и не перегружать основной сервер.

### Чем эти подходы отличаются

- `Партиционирование` делит большую таблицу на части внутри одного логического хранилища.
- `Шардирование` делит данные между разными серверами.
- `Репликация` не делит данные, а копирует их.

## Словарь простыми словами

Ниже собраны слова, которые часто встречаются в таких заданиях, но на практике звучат сложнее, чем есть на самом деле.

### ACID

`ACID` - это набор свойств, который делает работу с деньгами надежной.

- `Atomicity` - операция выполняется либо полностью, либо не выполняется совсем.
- `Consistency` - после операции данные остаются корректными.
- `Isolation` - параллельные операции не мешают друг другу.
- `Durability` - если операция подтверждена, она не потеряется даже после сбоя.

Для системы учета доходов и расходов это важно, потому что списание денег "наполовину" недопустимо.

### Реляционная база данных

Реляционная БД - это база, где данные хранятся в таблицах со строками, столбцами и связями между таблицами. Примеры: PostgreSQL, MySQL.

### PK и FK

- `PK` (`Primary Key`) - главный ключ таблицы, то есть поле, которое уникально определяет запись.
- `FK` (`Foreign Key`) - внешний ключ, то есть ссылка на запись в другой таблице.

Пример:

- `users.user_id` - это `PK`;
- `accounts.user_id` - это `FK`, который показывает, какому пользователю принадлежит счет.

### UUID

`UUID` - это длинный уникальный идентификатор, который почти невозможно случайно повторить. Его удобно использовать, когда данные создаются в распределенной системе.

### Range Partitioning

`Range Partitioning` - это разбиение данных по диапазонам значений. В этой работе диапазон - это время: один месяц, потом следующий месяц и так далее.

### Partition Pruning

`Partition Pruning` - это ситуация, когда СУБД понимает, что ей не нужно смотреть все партиции. Например, если запрос идет только за июнь 2026 года, база сразу пропускает май, апрель и остальные месяцы.

### Shard Key

`Shard Key` - это поле, по которому система понимает, в какой шард положить данные и откуда потом их читать. В этой работе таким ключом является `user_id`.

### Хэширование

Хэширование - это способ превратить значение в число по определенному алгоритму. Здесь это нужно не для безопасности, а для равномерного распределения пользователей по шардам.

### CRC32

`CRC32` - это одна из хэш-функций. В этой работе она используется для вычисления номера шарда:

`Shard_ID = CRC32(user_id) % N`

Проще говоря, система берет `user_id`, преобразует его в число и по остатку от деления определяет нужный сервер.

### Cross-shard JOIN

`Cross-shard JOIN` - это ситуация, когда для одного запроса приходится собирать данные сразу с нескольких шардов. Это медленно и сложно, поэтому в хорошем проектировании стараются сделать так, чтобы данные одного пользователя лежали вместе.

### Master и Replica

- `Master` или `Primary` - основной сервер, куда идут изменения данных.
- `Replica` - копия основного сервера, из которой обычно читают данные.

### Асинхронная репликация

Асинхронная репликация означает, что копии обновляются не строго в ту же миллисекунду, что и основной сервер, а с небольшой задержкой. Обычно это быстрее и проще для производительности, но из-за этого реплика может немного отставать.

### Failover

`Failover` - это автоматическое переключение на резервный сервер при сбое основного.

### Hotspot или "горячий" шард

`Hotspot` - это ситуация, когда один шард загружен намного сильнее остальных. Например, если один очень активный пользователь создает несоразмерно много транзакций.

### Решардинг

`Решардинг` - это перераспределение данных между шардами, когда старого количества серверов уже не хватает.

## Как это применено в решении

### 1. Структура базы данных

По ER-диаграмме в системе используются следующие основные сущности:

- `users` - пользователи;
- `accounts` - счета пользователя;
- `categories` - категории доходов и расходов;
- `transactions` - финансовые операции;
- `monthly_aggregates` - месячные агрегаты для быстрых отчетов.

Основные связи:

- один пользователь может иметь несколько счетов;
- один пользователь может иметь несколько категорий;
- один счет содержит много транзакций;
- одна категория может классифицировать много транзакций;
- по пользователю формируются агрегированные месячные показатели.

Отдельно важно, что в `categories` поле `user_id` может быть `NULL`. Это позволяет хранить не только пользовательские категории, но и системные.

### 2. Как выбрано партиционирование

Для партиционирования выбрана таблица `transactions`, потому что она растет быстрее остальных.

Выбран тип `RANGE` по полю даты транзакции. На диаграмме видно, что в качестве ключа партиционирования используется `transaction_date`, а сами партиции формируются по месяцам.

Пример структуры партиций:

- партиция `Май 2026`;
- партиция `Июнь 2026`;
- следующие месячные партиции по мере роста данных;
- отдельная партиция по умолчанию на случай нетипичных значений или ошибок маршрутизации.

Почему это разумно:

- в кошельке очень часто запрашивают данные за период;
- отчеты "за месяц" или "за квартал" читают только нужные куски таблицы;
- старые данные проще архивировать и обслуживать;
- индексы внутри каждой партиции меньше и работают быстрее.

Какие запросы выигрывают больше всего:

- список операций за конкретный месяц;
- сводка доходов и расходов за период;
- выборка последних операций пользователя;
- удаление или архивирование старых данных.

### 3. Как выбрано шардирование

Шардирование выполняется по `user_id`, потому что это естественный ключ для такой предметной области.

Логика простая: почти все действия пользователя связаны только с его собственными данными, поэтому выгодно хранить их вместе. Тогда запросы не прыгают между несколькими шардами.

На архитектурной схеме роутер определяет нужный шард через хеширование: вычисляется `CRC32(user_id)`, после чего берется остаток от деления на число шардов. То есть в общем виде используется формула:

`shard_id = CRC32(user_id) % N`

Где `N` - количество шардов. На схеме показан вариант с распределением по нескольким шардам, а выбор конкретного узла выполняет маршрутизатор.

Преимущества такого решения:

- данные пользователей распределяются более равномерно;
- легко понять, где искать данные конкретного пользователя;
- уменьшается количество межшардовых операций;
- проще масштабировать систему добавлением новых шардов.

### 4. Как выбрана репликация

Для каждого шарда используется схема:

- один `primary/master` для записи;
- две `replica` для чтения;
- асинхронная репликация от основного узла к копиям.

Это соответствует общей архитектурной диаграмме: запись идет в основной узел шарда, а запросы только на чтение можно отправлять на реплики.

Что это дает:

- основной узел не перегружается отчетными запросами;
- чтение можно масштабировать горизонтально;
- при отказе одной реплики система продолжает работать;
- при отказе `primary` можно выполнить переключение на одну из реплик.

Нужно учитывать и ограничение: при асинхронной репликации реплика может немного отставать от основного узла. Значит, сразу после записи пользователь теоретически может не увидеть самые свежие данные на одном из read-узлов.

### 5. Общая архитектура системы

По схеме работа выглядит так:

1. Клиент `Mobile / Web` отправляет HTTP-запрос.
2. Запрос сначала попадает в балансировщик `Nginx / HAProxy`.
3. Затем запрос идет в `API Gateway`.
4. Маршрутизатор определяет шард по `user_id`.
5. Если это запись, запрос уходит в `master` нужного шарда.
6. Если это чтение, запрос можно отправить на одну из `replica`.
7. Внутри каждого шарда таблица `transactions` дополнительно разбита на месячные партиции.

Получается двухуровневое масштабирование:

- на уровне серверов работает шардирование;
- внутри шарда для большой таблицы работает партиционирование.

В варианте из PDF на старте закладывается `4` шарда. Внутри каждого шарда работает схема `1 master + 2 replica`.

## Краткие ответы по анализу

### Почему выбран именно такой способ шардирования

Шардирование по `user_id` хорошо подходит для кошелька, потому что данные одного пользователя чаще всего используются вместе. Это уменьшает сложность запросов и делает маршрутизацию предсказуемой.

### Какие преимущества дает партиционирование

Партиционирование уменьшает объем данных, которые нужно прочитать при запросах за период. За счет этого ускоряются отчеты, упрощается обслуживание таблицы и архивирование старых записей.

Отдельный практический плюс: старые данные можно удалять или переносить не построчно, а сразу целой партицией. Это намного быстрее и безопаснее для нагруженной таблицы.

### Возможные проблемы системы

- неравномерная нагрузка на шарды, если часть пользователей намного активнее остальных;
- отставание реплик от `primary`;
- усложнение миграций и сопровождения по сравнению с одной обычной базой;
- более сложная логика для глобальной аналитики по всем пользователям сразу.

### Как систему можно масштабировать дальше

- увеличивать количество шардов;
- добавлять новые read-replica;
- выносить тяжелую аналитику в отдельный контур;
- автоматизировать failover и мониторинг репликации;
- использовать ребалансировку данных при росте нагрузки.

## Итог

В этом решении партиционирование, шардирование и репликация используются не как три отдельные идеи, а как части одной архитектуры.

- `Партиционирование` ускоряет работу с большой таблицей транзакций.
- `Шардирование` распределяет пользователей между несколькими узлами.
- `Репликация` повышает отказоустойчивость и ускоряет чтение.

Именно такая комбинация хорошо подходит для системы учета доходов и расходов, где много операций, много запросов за период и важна непрерывная доступность данных.
