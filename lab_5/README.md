# Лабораторная работа 5

## Kafka: topic, partitions, producer и consumer group

В этой лабораторной работе показывается, как Kafka передает сообщения о транзакциях между сервисами. Один сервис `producer` отправляет события в Kafka, а два сервиса `consumer` читают их из общего `topic`.

На примере этой работы можно понять:

- зачем в Kafka нужен `topic`;
- что такое `partition`;
- как `key` влияет на распределение сообщений;
- зачем нужна `consumer group`;
- что такое сериализация и десериализация.

## Идея работы простыми словами

Представим, что в системе появляются финансовые операции пользователей: пополнение счета, списание, перевод. Вместо прямой передачи данных от одного сервиса к другому можно использовать Kafka как промежуточный слой.

Логика такая:

1. `Producer` формирует сообщение о транзакции.
2. Отправляет его в Kafka.
3. Kafka кладет сообщение в нужный `topic` и в одну из его `partition`.
4. `Consumer` подписывается на этот `topic` и читает сообщения.

Это удобно, когда нужно обрабатывать поток событий последовательно, надежно и с возможностью масштабирования.

## Что такое Kafka простым языком

Kafka - это система передачи сообщений. Ее можно представить как очень быстрый и устойчивый журнал событий, куда одни сервисы записывают сообщения, а другие их читают.

Kafka особенно удобна, когда:

- сообщений много;
- данные приходят постоянно;
- нужно разделить отправителя и получателя;
- обработку нужно масштабировать на несколько сервисов.

## Простое объяснение терминов

### Что такое topic

`Topic` - это логический канал или "лента" сообщений.

В этой лабораторной работе используется topic:

```text
transactions
```

Именно туда producer отправляет события о транзакциях.

Если совсем просто, `topic` можно представить как отдельную очередь для сообщений определенного типа.

### Что такое partition

`Partition` - это часть topic.

Один topic может быть разделен на несколько partitions. В этой работе их `3`.

Зачем это нужно:

- сообщения можно распределять между несколькими частями;
- чтение можно распараллелить;
- Kafka может обслуживать больше нагрузки.

Важно понимать: `topic` один, но внутри него несколько partitions.

### Что такое producer

`Producer` - это приложение, которое отправляет сообщения в Kafka.

В этой работе producer создает topic `transactions`, а затем отправляет туда `10` JSON-сообщений о транзакциях пользователей.

### Что такое consumer

`Consumer` - это приложение, которое читает сообщения из Kafka.

В этой лабораторной работе запущены два consumer-а:

- `consumer-1`;
- `consumer-2`.

Они читают сообщения из одного topic.

### Что такое key сообщения

`Key` - это значение, по которому Kafka решает, в какую partition положить сообщение.

В этой работе в качестве ключа используется:

```text
user_id
```

Это очень важно, потому что Kafka отправляет сообщения с одинаковым ключом в одну и ту же partition.

Значит:

- все сообщения пользователя `101` попадут в одну partition;
- все сообщения пользователя `202` тоже попадут в одну partition;
- но уже, возможно, в другую.

Именно это и требуется в задании.

### Что такое consumer group

`Consumer group` - это группа consumer-ов, которые читают один и тот же topic совместно.

В этой лабораторной работе используется группа:

```text
transaction-group
```

Смысл группы в том, что Kafka сама делит partitions между consumer-ами внутри группы.

Это означает:

- если consumer-ов два, Kafka распределит между ними partitions;
- одно сообщение внутри одной группы обрабатывается только одним consumer-ом;
- дублирования внутри одной группы не возникает.

### Что такое сериализация

Сериализация - это преобразование объекта программы в формат, который можно отправить по сети или сохранить.

В этой работе сообщение превращается в `JSON`, а затем в `bytes`.

Пример сообщения:

```json
{
  "user_id": 101,
  "amount": 500,
  "type": "incoming"
}
```

### Что такое десериализация

Десериализация - это обратный процесс. Consumer получает `bytes`, потом превращает их обратно в JSON-объект, чтобы можно было работать с полями `user_id`, `amount`, `type`.

### Что такое offset

`Offset` - это номер сообщения внутри partition.

Он показывает, какое по счету сообщение хранится в этой partition. Благодаря offset Kafka понимает, какие сообщения consumer уже прочитал, а какие еще нет.

По заданию нужно:

В текущем решении это реализовано так:

- topic: `transactions`;
- partitions: `3`;
- consumer group: `transaction-group`;

- формат: JSON;
- ключ сообщения: строковое представление `user_id`.

## Что запускается

- `lab5-zookeeper` - Zookeeper для Kafka;
- `lab5-kafka` - Kafka broker;
- `lab5-producer` - producer, который отправляет сообщения;

- `lab5-consumer-2` - второй consumer.

## Как работает producer

Producer сначала ждет, пока Kafka станет доступна. После этого он:

1. Создает topic `transactions`.
2. Указывает `3` partition и `replication_factor=1`.
3. Формирует список сообщений.
4. Для каждого сообщения берет `user_id`.
5. Использует `user_id` как `key`.
6. Отправляет сообщение в Kafka.

Сообщения в коде выглядят примерно так:

```json
{
  "user_id": 101,
  "amount": 1500.0,
  "type": "incoming"
}
```

В коде producer использует:

- `key_serializer` для преобразования ключа в `bytes`;
- `value_serializer` для преобразования словаря в JSON;
- `acks="all"` для более надежного подтверждения записи.

## Как работает consumer

Consumer тоже сначала ждет доступности Kafka, а затем:

1. Подписывается на topic `transactions`.
2. Входит в группу `transaction-group`.
3. Читает сообщения с начала, если раньше не читал их (`auto_offset_reset="earliest"`).
4. Десериализует сообщение.
5. Печатает в логах partition, offset, key и содержимое сообщения.

Два consumer-а работают в одной группе, поэтому Kafka автоматически делит partitions между ними.

## Почему одинаковый user_id попадает в одну partition

Это ключевая идея лабораторной работы.

Kafka использует `key` сообщения для выбора partition. Если у двух сообщений одинаковый ключ, Kafka направит их в одну и ту же partition.

Так как в этой работе ключ - это `user_id`, получается:

- транзакции одного пользователя читаются в одном логическом потоке;
- порядок сообщений пользователя сохраняется внутри partition;
- обработка становится более предсказуемой.

Например:

- сообщения с `user_id=101` попадут в одну partition;
- сообщения с `user_id=505` тоже будут идти в одну partition;
- но пользователи `101` и `505` могут оказаться в разных partitions.

Именно поэтому в логах producer видно, что одинаковый `user_id` каждый раз уходит в один и тот же partition.

## Почему два consumer-а не читают одно и то же сообщение

Потому что они входят в одну `consumer group`.

Kafka работает так:

- у каждой partition внутри группы есть только один активный consumer;
- если partitions три, а consumer-ов два, один consumer получит одну partition, другой - две;
- если один consumer остановится, Kafka перераспределит partitions между оставшимися.

То есть Kafka сама делает балансировку чтения внутри группы.

## Что смотреть в логах

Логи producer:

```bash
docker compose logs -f producer
```

Там видно:

- `user_id`;
- тип транзакции;
- сумму;
- в какую `partition` ушло сообщение;
- какой у сообщения `offset`.

Если несколько сообщений имеют одинаковый `user_id`, partition у них должна совпадать.

Логи consumer-ов:

```bash
docker compose logs -f consumer-1 consumer-2
```

Там видно:

- какой consumer прочитал сообщение;
- из какой partition оно пришло;
- какой у него key;
- какой `user_id`, `type` и `amount` были внутри.

Можно смотреть все сразу:

```bash
docker compose logs -f producer consumer-1 consumer-2
```

## Что должно получиться

- Kafka и Zookeeper успешно запускаются;
- topic `transactions` создается автоматически;
- producer отправляет сообщения в JSON-формате;
- одинаковые `user_id` попадают в одну и ту же partition;
- разные `user_id` распределяются по partitions;
- два consumer-а читают сообщения в одной `consumer group`;
- Kafka сама делит partitions между consumer-ами;
- одно сообщение внутри группы не дублируется между consumer-ами.

## Итог

Эта лабораторная работа показывает, как Kafka помогает передавать события между сервисами и параллельно обрабатывать поток сообщений.

Главные идеи здесь такие:

- `topic` - это канал сообщений;
- `partition` - это часть topic;
- `key` определяет, в какую partition попадет сообщение;
- одинаковый `user_id` попадает в одну и ту же partition;
- `consumer group` позволяет нескольким consumer-ам делить работу между собой;
- сериализация и десериализация позволяют передавать обычные Python-данные через Kafka в виде JSON.
